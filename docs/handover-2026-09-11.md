```bash

cd src-tauri && cargo run --example probe_threads -- --find-thread <threadId>
```

**端到端必走一遍**（同进程验证通过 ≠ 功能可用）：

1. 新建会话 → 发消息 → 确认它出现在侧边栏且被选中
2. 切换会话 / 重启应用
3. 回收站恢复
4. 悬停轮标题 → 「回退到此前」（会丢弃之后的轮次，**不会撤销文件改动**）
5. 长会话 `/compact`（**旧轮次会从界面上消失**）
6. 让 agent 跑长任务，中途打字发送（应插话到当前轮）

## 5. 接手必须先知道的坑

### 5.1 协作类（这个仓库特有）

1. **Flydex 每轮结束会对当前工作目录 `git add -A && git commit`**
   —— 在 flydex 仓库里开发 Flydex 时，你的改动可能在写完提交信息前就被
   `flydex-checkpoint <时间戳>` 提交掉（本次开发中发生过，提交说明丢失、历史被无说明快照穿插）。
   `git status` 显示 "nothing to commit" 而改动确实存在时，就是这种情况。
2. **不要在同一个仓库跑两个 agent**。本次开发中用 Flydex 的 agent 改 Flydex 自己，
   出现过：我的临时诊断代码被对方删掉、对方加的改动以无说明快照混入历史，
   而我一度把对方的编辑误判成"文件被还原"，绕了弯路。
3. **`custom-protocol` 会把 `dist/` 编译进二进制** —— 要用打包的 exe 验证前端改动，
   必须**先 `vite build` 再 `cargo build`**。`pnpm tauri dev` 不受影响。

### 5.2 codex 协议类

完整 9 条见 `AGENTS.md` §2.5。最容易踩的三条：

- `thread/turns/list` **必须显式传 `itemsView: "full"`**（缺省是 `Summary`，实测丢 37% 的 item）
- `thread/list` **必须显式传 `modelProviders: []`**（否则自家会话被整片过滤）
- **排查"某条数据看不见"时，先找"决定可见性的条件全集"**（读
  `codex-rs/state/src/runtime/threads.rs` 的 `push_thread_filters`），
  逐条排除；不要在参数空间里穷举 —— 本次穷举了 6 轮才去读源码，一读就看到决定性条件。

### 5.3 方法论教训（本次代价最大的两条）

1. **相关 ≠ 因果**。我曾看到"3 个不可见的样本都是 paginated"，就断定 paginated 导致不可见，
   并据此**撤掉了一个本来可用的功能**（回退）。实际那些样本**同时**被 provider 过滤，
   还有一个后来被归档了 —— 三重混淆叠在一起。
2. **端到端要覆盖真实用户路径**。P11 验证 paginated"一切照常"结论没错，
   但那是在**同一个 daemon 会话内**测的；而"新建会话"这条路径我一次都没点过，
   用户一点就撞出三个 bug。
